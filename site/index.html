02

"attack my application"

The orchestrator is a documented workflow for a compatible coding agent. The orchestrator detects what your app is — reading the code you built, or probing a running app — builds a surface × technique matrix, and drives the whole library in kill-chain order.

  1. 00

    authorization gate

    Hard stop. Ownership, scope, window, and data-handling confirmed before a single active probe.

  2. 01

    map the surface

    Reads your code — or a running app — for stack, entry points, and session model, into a surface map.

  3. 02

    select

    Lights up the matrix — routes each input to the skills whose preconditions it satisfies.

  4. 03

    run in kill-chain order

    Recon → injection → access control → auth → client-side. Minimal proof first.

  5. 04

    verify detection

    Guides the agent to check the paired defense where telemetry and a test environment are available.

  6. 05

    report

    Prioritized findings, per-screen risk, reproduction, remediation, and coverage.

attack-my-application — sample report
FINDINGS (worst first)
 HIGH  IDOR on /profile?id=
       sequential ids expose other users
       → web-access-control-monitoring
 MED   Reflected XSS on /search

03

Start with a scoped assessment

No security background needed. Install the library into your agent, point it at an app you own, and let it work.

zsh — your project
# Current website content is on this PR branch (not yet in a release)
$ git clone --branch codex/clean-site-unscoped-package https://github.com/praneeth132006/RedBlueSkills.git
$ cd RedBlueSkills
# Install playbooks into this project, or pass --dest for another project
$ node bin/cli.js init

# 2 · read the source installation guide
$ node bin/cli.js quickstart

# or grab one skill — its pair comes along
$ node bin/cli.js add web-sql-injection

  1. install

    init copies skills/ and orchestrators/ into ./.claude/skills/redblueskills.

  2. instruct

    Tell your agent: "attack my application — it's my own code and I authorize testing." With no URL it reviews the code in your project; add at <url> to probe a running app.

  3. confirm the gate

    Ownership, scope, window, data-handling. A hard stop before anything active runs.

  4. read the report

    Findings, per-screen risk, coverage, and a fix list linked to each defense skill.

04

Built for evidence

Clear instructions, documented limitations, and reproducible checks.

  1. [a]

    Agent-readable instructions

    Each SKILL.md documents prerequisites, scope, steps, evidence, and its defensive or offensive counterpart.

  2. [b]

    bound red ⟷ blue

    Every offensive technique links to a detection or hardening skill. CI checks that each pairing points in both directions.

  3. [c]

    Transparent validation

    Validation metadata records who tested a skill, when, and against which lab. Reviewed skills remain distinct from validated ones; fixture results have explicit limits.

  4. [d]

    Reproducible checks

    Schema checks, content hashes, package installation tests, and offline regression labs help catch errors before a release.

05

add your own pair

The library scales with contributors, not with one author. A red skill ships with the blue skill that detects it — and CI enforces that the pairing is real.

  1. copy the template

    cp -r _template skills/<app>/<team>/<stage>/<name>

  2. author both sides

    The offensive skill and the detection it pairs with — each one listing the other.

  3. validate

    Against _lab/ or a CTF target, then stamp who validated it and when.

  4. run the gate

    make check — schema, bidirectional pairing, catalog freshness, tests.

zsh — RedBlueSkills
$ make install
$ cp -r _template skills/web-app/red/…/my-skill
# …author SKILL.md + its paired blue skill…
$ make check     # the same gate CI runs
$ make catalog   # refresh catalog.json + INDEX.md
